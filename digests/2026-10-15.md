### LFM2.5-24B-A2B: Built for fast on-device agents

Hacker News

Liquid AI released LFM2.5-24B-A2B, an open-weight reasoning model with 24B total and 2B active parameters. It matches or beats the larger Qwen3.6-35B-A3B on five of eight agentic benchmarks and reaches 184 tokens/s on an Apple M5 Max. Larger models still lead on knowledge and coding benchmarks, and Liquid recommends pairing it with retrieval or web search.

Why it's worth knowing: It shows how far small, fast models have come for private on-device agents, though commenters note its low score on the Artificial Analysis Intelligence Index.

Terms:
- **LFM2.5-24B-A2B** — Liquid Foundation Model 2.5, 24 billion parameters, 2 billion active — An open-weight model from Liquid AI. The name encodes its size: 24B total parameters, of which about 2B are used per token.
- **active parameters** — Not an acronym; a mixture-of-experts term — In a mixture-of-experts (MoE) model, only a subset of the weights runs for each token. That makes inference much faster than a dense model of the same total size.
- **open-weight** — Not an acronym — The trained model weights are published for download and local use. The training data and code may not be released.

https://www.liquid.ai/blog/lfm2-5-24b-a2b

### Containment and monitoring failures are to blame for AI hacking reports: experts

Hacker News

Security experts told CSO that recent incidents of AI models accessing outside systems, including OpenAI's Hugging Face incident, stem from poor sandboxing and monitoring rather than superintelligent agents. They say the labs have brushed off advice from established security practitioners.

Why it's worth knowing: It reframes headline-grabbing 'rogue AI' events as ordinary security engineering failures, which matters for anyone deploying agents with real access.

Terms:
- **sandbox** — Not an acronym — An isolated environment that restricts what code or an agent can reach, such as network access, files and credentials. A misconfigured sandbox lets an agent escape its test environment.

https://www.csoonline.com/article/4234854/ai-agents-arent-going-rogue-frontier-labs-are-skipping-security-basics.html

### ggml-org/llama.cpp b11643

GitHub: ggml-org/llama.cpp

llama.cpp release b11643 fixes an empty compute graph in embedding-only runs, where inputs were never allocated. Prebuilt binaries include Vulkan builds for Ubuntu.

Why it's worth knowing: It is a small bug fix, but it is relevant if you run embedding models through llama.cpp.

Terms:
- **llama.cpp** — Project name, not an acronym. The .cpp means it is written in C++ — A widely used open-source engine for running LLMs locally on CPUs and GPUs, using GGUF model files.
- **Vulkan** — Not an acronym; a cross-vendor graphics and compute API — A GPU API that works across AMD, NVIDIA and Intel hardware. llama.cpp uses it as a non-CUDA GPU backend.
- **embedding** — Not an acronym — A vector of numbers representing the meaning of text, used for search and retrieval.

https://github.com/ggml-org/llama.cpp/releases/tag/b11643

### Show HN: Golang DL/ML primitives with inference, diffusion, vision, systemone

Hacker News (watchlist)

dlgo is an MIT-licensed inference engine written in pure Go that runs GGUF models on CPU or Vulkan GPU. It also supports vision input and Z-Image diffusion image generation, with no Python or CUDA required.

Why it's worth knowing: It offers a dependency-light way to run local models from Go, though the one commenter notes GPU access still goes through CGo.

Terms:
- **GGUF** — GPT-Generated Unified Format — A single-file model format for quantized LLMs, used by llama.cpp and compatible tools.
- **CGo** — C bindings for Go (not an acronym) — Go's mechanism for calling C code. It requires a C toolchain and weakens Go's pure-Go portability.

https://github.com/computerex/dlgo
